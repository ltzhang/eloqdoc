## 1. Index Types — Changes in 8.0

### 1.1 `INDEX_TYPE_COUNT` Sentinel

**Added in 8.0.** `INDEX_TYPE_COUNT` is appended as the last value in the `IndexType` enum. It is not a real index type — it is a sentinel representing the total number of index types, used for array sizing and bounds checking.

```cpp
enum IndexType {
    INDEX_BTREE,
    INDEX_COLUMN,
    INDEX_2D,
    INDEX_ENCRYPTED_RANGE,
    INDEX_HAYSTACK,
    INDEX_2DSPHERE,
    INDEX_2DSPHERE_BUCKET,
    INDEX_TEXT,
    INDEX_HASHED,
    INDEX_WILDCARD,
    INDEX_TYPE_COUNT    // NEW: not a real index; used as array bound
};
```

**User impact:** None — this is an internal C++ enum bookkeeping change.

### 1.2 Column Store Index Deprecated in 8.0

The `"columnstore"` index type (`INDEX_COLUMN`) is **deprecated** in 8.0. Existing indexes continue to work, but new creation emits a deprecation warning. Users should monitor whether MongoDB removes this in a future major version.

## 2. Search Index Commands (New in 8.0)

**Source:** `src/mongo/db/commands/search_index_commands.cpp`  
**IDL:** `src/mongo/db/commands/search_index_commands.idl`

MongoDB 8.0 adds server-side commands to manage **Atlas Search indexes** and **Vector Search indexes**. Previously these were managed only through Atlas UI or API. These commands work when a `mongot` search daemon is configured (required for Atlas or self-managed Atlas Search).

### 2.1 `createSearchIndex`

```js
db.runCommand({
  createSearchIndex: "<collection>",
  indexes: [{
    name: "<indexName>",
    definition: {
      mappings: {
        dynamic: true | false,
        fields: { ... }
      }
    }
  }]
})
```

Returns: `{ indexesCreated: [{ id: "<id>", name: "<name>" }] }`

### 2.2 `dropSearchIndex`

```js
db.runCommand({
  dropSearchIndex: "<collection>",
  name: "<indexName>"
})
```

Or by ID:
```js
db.runCommand({
  dropSearchIndex: "<collection>",
  id: "<indexId>"
})
```

### 2.3 `updateSearchIndex`

```js
db.runCommand({
  updateSearchIndex: "<collection>",
  name: "<indexName>",
  definition: { ... }
})
```

### 2.4 `listSearchIndexes`

Via aggregation stage:
```js
db.collection.aggregate([{
  $listSearchIndexes: {
    name: "<indexName>"   // optional filter
  }
}])
```

Returns: `{ id, name, status, queryable, latestDefinition, ... }`

**Status values:** `BUILDING`, `READY`, `STALE`, `PENDING`, `DELETING`, `FAILED`.

**Source:** `src/mongo/db/pipeline/search/document_source_list_search_indexes.cpp`

### 2.5 Architecture: `mongot` Integration

Search index commands are forwarded to the `mongot` search process via `SearchIndexProcessInterface`:
- `src/mongo/db/commands/search_index_commands.cpp` — command handlers
- `src/mongo/db/exec/search/` — execution layer
- `src/mongo/db/pipeline/search/` — pipeline stages for search

The `mongot` process manages the actual Lucene-based search index. MongoDB acts as a proxy, forwarding search index management operations.

## 3. Vector Search — `$vectorSearch` (New in 8.0)

**Source:** `src/mongo/db/pipeline/search/document_source_vector_search.cpp`  
**Stage name:** `$vectorSearch`

Performs Approximate Nearest Neighbor (ANN) search using vector embeddings stored in documents.

### 3.1 `$vectorSearch` Syntax

```js
{ $vectorSearch: {
    index: "<vectorIndexName>",
    path: "<fieldName>",           // field containing the vector
    queryVector: [<float>, ...],   // query embedding (dense vector)
    numCandidates: <int>,          // number of candidates to consider (>= limit)
    limit: <int>,                  // number of results to return
    filter: <MQL filter>,          // optional pre-filter
    exact: false                   // false = ANN; true = exact (ENN, slower)
}}
```

**Fields:**

| Field | Type | Required | Notes |
|---|---|---|---|
| `index` | string | yes | Name of the vector search index |
| `path` | string | yes | Field path containing the vector array |
| `queryVector` | array of float | yes | The query vector to find neighbors for |
| `numCandidates` | int | yes (for ANN) | Must be >= `limit`; higher = better recall, slower |
| `limit` | int | yes | Number of results to return |
| `filter` | object | no | Pre-filter on non-vector fields |
| `exact` | bool | no | `true` = exact search (KNN, slower but perfect recall) |

**Must be the first stage** in the aggregation pipeline.

**Output:** Documents enriched with a `$meta: "vectorSearchScore"` field accessible via:
```js
{ $project: { score: { $meta: "vectorSearchScore" } } }
```

### 3.2 Vector Search Index Creation

Vector indexes are created via `createSearchIndex` with a vector-specific definition:
```js
db.runCommand({
  createSearchIndex: "embeddings",
  indexes: [{
    name: "vector_idx",
    type: "vectorSearch",
    definition: {
      fields: [{
        type: "vector",
        path: "embedding",
        numDimensions: 1536,
        similarity: "cosine" | "euclidean" | "dotProduct"
      }]
    }
  }]
})
```

**`similarity` options:**
| Value | Distance metric | Use case |
|---|---|---|
| `"cosine"` | Cosine similarity | Normalized embeddings (most common) |
| `"euclidean"` | Euclidean (L2) distance | Raw numeric vectors |
| `"dotProduct"` | Dot product | Pre-normalized unit vectors (fastest) |

## 4. Rank Fusion and Scoring (New in 8.0)

### 4.1 `$rankFusion`

**Source:** `src/mongo/db/pipeline/document_source_rank_fusion.cpp`  
**IDL:** `src/mongo/db/pipeline/document_source_rank_fusion.idl`

Combines results from multiple sub-pipelines using Reciprocal Rank Fusion (RRF), a standard method for merging ranked lists without requiring score normalization.

```js
{ $rankFusion: {
    input: {
      pipelines: {
        bm25search: [
          { $search: { text: { query: "quantum computing", path: "body" } } }
        ],
        vectorSearch: [
          { $vectorSearch: { index: "vec_idx", path: "embedding", queryVector: [...], numCandidates: 100, limit: 10 } }
        ]
      }
    },
    combination: {
      weights: {
        bm25search: 1,
        vectorSearch: 1
      }
    }
}}
```

**Fields:**

| Field | Type | Notes |
|---|---|---|
| `input.pipelines` | map of name → pipeline | Named sub-pipelines whose results are fused |
| `combination.weights` | map of name → float | Optional weights per pipeline (default 1.0) |

**RRF formula:** `score = Σ (weight / (k + rank_i))` where `k=60` by default.

### 4.2 `$scoreFusion`

Similar to `$rankFusion` but uses raw scores (not ranks) from each pipeline. Each pipeline must output a `score` field.

```js
{ $scoreFusion: {
    input: { pipelines: { ... } },
    combination: {
      weights: { pipe1: 0.7, pipe2: 0.3 }
    },
    normalization: "l2" | "minMaxScaler" | "none"
}}
```

### 4.3 `$score`

Returns the search score for the current document (from `$search`, `$vectorSearch`, or scoring stages):

```js
{ $project: {
    searchScore: { $meta: "searchScore" },
    vectorScore: { $meta: "vectorSearchScore" }
}}
```

## 5. Query Settings (New in 8.0)

### 5.1 `setQuerySettings` Command

**Source:** `src/mongo/db/commands/query_settings_cmds.cpp`

Administrators can attach query settings (hints, limits) to query shapes — persistent query plan hints that apply every time the same query shape is executed, across all cluster members.

```js
db.adminCommand({
  setQuerySettings: {
    find: "<collection>",
    filter: { status: "active" },
    sort: { date: -1 }
  },
  settings: {
    indexHints: [{
      ns: { db: "mydb", coll: "<collection>" },
      allowedIndexes: ["status_1_date_-1"]
    }],
    queryFramework: "classic" | "sbe" | "tryBonsai" | "tryBonsaiExperimental"
  }
})
```

**`settings` fields:**

| Field | Type | Notes |
|---|---|---|
| `indexHints` | array | Force or restrict which indexes the planner uses |
| `queryFramework` | string | Force a specific query execution framework |
| `reject` | bool | Reject all executions of this query shape with an error |

### 5.2 `removeQuerySettings` Command

```js
db.adminCommand({
  removeQuerySettings: {
    find: "<collection>",
    filter: { status: "active" },
    sort: { date: -1 }
  }
})
```

### 5.3 `$querySettings` Pipeline Stage

Returns current query settings for viewing:
```js
db.aggregate([{ $querySettings: {} }])
```

## 6. Time-Series: Upsert Support (New in 8.0)

**Source:** `src/mongo/db/exec/timeseries/timeseries_upsert.cpp`

In 8.0, `updateOne` / `updateMany` with `upsert: true` now works on time-series collections:

```js
db.sensors.updateOne(
  { device: "sensor-1", timestamp: ISODate("2024-01-01T00:00:00Z") },
  { $set: { temperature: 72.5 } },
  { upsert: true }
)
```

**Behavior:**
- If a document matching the filter exists: update in-place.
- If no match: insert a new document (must include `timeField` in the filter or `$setOnInsert`).

**Restriction:** The `timeField` cannot be updated; only `metaField` sub-fields and measurement fields can be modified.

## 7. FLE2: `cleanupStructuredEncryptionData` (New in 8.0)

**Source:** `src/mongo/db/commands/fle2_cleanup_cmd.cpp`  
**IDL:** `src/mongo/db/commands/fle2_cleanup.idl`

Removes obsolete documents from FLE2 internal state collections. More aggressive than `compactStructuredEncryptionData`:

```js
db.runCommand({
  cleanupStructuredEncryptionData: "<collection>",
  cleanupTokens: { <field>: BinData(...), ... }
})
```

**Difference from `compact`:**
- `compactStructuredEncryptionData` — merges and compacts ESC/ECC documents.
- `cleanupStructuredEncryptionData` — removes deleted documents from the ECOC (Encrypted Collection Offset Collection).

These two operations should be run periodically on collections with frequent updates/deletes of encrypted fields.

## 12. Internal Architecture Changes in 8.0

### 12.1 Processor-Based Pipeline Architecture

In 8.0, several pipeline stages are refactored into dedicated "processor" classes (replacing the `inner_pipeline_stage` abstraction):
- `GroupProcessor` — handles `$group` execution
- `MatchProcessor` — handles `$match` execution within a sub-pipeline
- `MergeProcessor` — handles `$merge` execution
- `RedactProcessor` — handles `$redact` execution
- `SingleDocumentTransformationProcessor` — handles `$project`/`$addFields`/`$replaceRoot`
- `UnwindProcessor` — handles `$unwind` execution

This is an internal refactoring; the user-facing API for all these stages is unchanged.

### 12.2 SBE Pushdown (8.0)

**Source:** `src/mongo/db/pipeline/sbe_pushdown.cpp`

The Slot-Based Execution (SBE) engine is enhanced to support more pipeline stages being "pushed down" into SBE for faster execution. Affects `$group`, `$lookup`, and other stages. Transparent to users (no API changes).

## 15. Breaking Changes from 7.0 → 8.0

1. **Column store index deprecated:** New creation emits deprecation warning; plan for migration.
2. **Internal pipeline stage changes:** `inner_pipeline_stage_impl` removed; replaced by processors — affects any code extending these classes (C++ plugin API).
3. **`$_internalChangeStreamHandleTopologyChange` versioned:** v2 variant added; old v1 format still accepted.
4. **`change_stream_helpers_legacy.cpp` removed:** Legacy helper code eliminated; any code relying on legacy change stream format handling must upgrade.
