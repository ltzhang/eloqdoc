# MongoDB 4.4 — API Delta from 4.2

**Source branch:** `origin/v4.4`  
**Baseline:** [v4.2_api.md](v4.2_api.md)  
**Format:** Explicit Added / Modified / Removed sections.

## Summary of 4.4 Changes (Data Model Focus)

| Area | Change |
|---|---|
| **Aggregation stages** | New `$unionWith` stage |
| **Accumulators** | New `$accumulator` (custom JS reducer) in `$group` |
| **Expressions** | New `$function` (custom JS expression); `$first`/`$last` as expressions |
| **Index builds** | Two-phase index builds with `commitQuorum` |
| **Projections** | `$` operator and `$elemMatch` clarifications |
| **Find** | `allowDiskUse` more formally supported |
| **Auth** | Certificate rotation command |
| **FCV** | Downgrade path changes |

## 1. Index Types — Changes in 4.4

**No new index types added in 4.4.** Index types remain the same as 4.2: btree, 2d, haystack, 2dsphere, text, hashed, wildcard.

### 1.1 Two-Phase Index Builds and `commitQuorum`

**Added in 4.4.** The `createIndexes` command gains a new top-level option:

```js
db.runCommand({
  createIndexes: "<collection>",
  indexes: [ <spec>, ... ],
  commitQuorum: "votingMembers" | "majority" | <int> | "0"
})
```

| Value | Meaning |
|---|---|
| `"votingMembers"` | Wait for all voting members to build the index |
| `"majority"` | Wait for a majority of voting members |
| `<int>` | Wait for exactly N members |
| `"0"` (or `0`) | No quorum; primary commits immediately |

**Default:** `"votingMembers"`.

**Background:** Prior to 4.4, index builds held a collection-level write lock for the duration of the build. In 4.4, the index is built in a background manner on all replica set members simultaneously, and a `voteCommitIndexBuild` message is sent when each member finishes. The primary only commits when the quorum is reached.

**Effect on `background` option:** The `background` option in the index spec is **ignored** in 4.4 and later, because all index builds are now "background" by default.

### 1.2 GeoHaystack Deprecated

GeoHaystack indexes are **deprecated** in 4.4 (still creatable, but will be rejected in 5.0).

## 2. Aggregation Pipeline — Changes

### 2.1 New Stage: `$unionWith`

**Source:** `src/mongo/db/pipeline/document_source_union_with.cpp`  
**IDL:** `src/mongo/db/pipeline/document_source_union_with.idl`

Performs a SQL-style `UNION ALL` of two collections' pipeline results.

```js
{ $unionWith: {
    coll: "<collection>",
    pipeline: [ <stage>, ... ]   // optional; applied to the other collection
}}
```

Shorthand (no pipeline on the other collection):
```js
{ $unionWith: "<collection>" }
```

**Behavior:**
- Combines documents from the current pipeline with documents from the specified `coll` (with optional `pipeline`).
- Does **not** deduplicate (use `$group` or `$sort` + `$group` afterward for deduplication).
- Both collections must be in the same database.
- Cross-database `$unionWith` is supported: `{ coll: "otherDb.coll" }`.
- Supports sharded collections.

**Use cases:** Combining results from multiple collections with the same schema, implementing multi-collection searches, log aggregation.

### 2.2 New Accumulator: `$accumulator`

**Source:** `src/mongo/db/pipeline/accumulator_js_reduce.cpp`

Allows defining a custom accumulator using JavaScript functions, usable inside `$group`.

```js
{ $group: {
    _id: "$category",
    result: {
      $accumulator: {
        init: <JavaScript function string>,         // () => initialState
        initArgs: [ <expression>, ... ],            // args passed to init()
        accumulate: <JavaScript function string>,    // (state, val, ...) => newState
        accumulateArgs: [ <expression>, ... ],       // per-document args to accumulate()
        merge: <JavaScript function string>,         // (state1, state2) => mergedState
        finalize: <JavaScript function string>,      // optional; (state) => result
        lang: "js"
      }
    }
}}
```

**Fields:**

| Field | Type | Required | Description |
|---|---|---|---|
| `init` | JS function string | yes | Initialize accumulator state |
| `initArgs` | array of expressions | no | Arguments passed to `init` |
| `accumulate` | JS function string | yes | Process each document; returns new state |
| `accumulateArgs` | array of expressions | yes | Per-document values passed to `accumulate` |
| `merge` | JS function string | yes | Merge two partial states (for sharding/spilling) |
| `finalize` | JS function string | no | Transform state into final output |
| `lang` | string | yes | Must be `"js"` |

**Requirement:** JavaScript must be enabled on the server (`--enableJavaScriptCoder` is always on in community edition but can be disabled in configuration).

### 2.3 New Expression: `$function`

**Source:** Expression handling in `src/mongo/db/pipeline/expression.cpp`

Allows running arbitrary JavaScript as an aggregation expression:

```js
{ $function: {
    body: <JavaScript function string>,  // function(arg1, arg2, ...) { return ...; }
    args: [ <expression>, ... ],
    lang: "js"
}}
```

**Example:**
```js
{ $addFields: {
    slug: {
      $function: {
        body: "function(name) { return name.toLowerCase().replace(/ /g, '-'); }",
        args: ["$name"],
        lang: "js"
      }
    }
}}
```

**Restriction:** Cannot be used in `$match` queries (only in projection/transformation stages).

### 2.4 `$first` and `$last` as General Expressions

In 4.4, `$first` and `$last` can be used as **expressions** (not just group accumulators):
```js
{ $project: { firstTag: { $first: "$tags" } } }  // first element of array
{ $project: { lastTag:  { $last:  "$tags" } } }   // last element of array
```

Previously these only worked as `$group` accumulators; now they work as array element accessors anywhere in the pipeline.

### 2.5 `$accumulate` Improvements (`$sum`, `$avg`, etc.)

`$sum`, `$avg`, `$min`, `$max` can now be used in `$project` and `$addFields` as array reduction expressions:
```js
{ $project: { total: { $sum: "$prices" } } }  // sum all elements in "prices" array
```

This was partially supported before, but 4.4 makes it fully consistent.

## 3. `find` Command — Changes

### 3.1 `allowDiskUse` Formalized

`allowDiskUse: true` is now formally part of the `find` command interface and is honored for `$sort` stages within a find. In 4.0/4.2 it was present but not consistently enforced.

```js
db.runCommand({
  find: "orders",
  sort: { total: -1 },
  allowDiskUse: true
})
```

## 4. CRUD Changes

### 4.1 Projection Clarifications

In 4.4, the positional projection operator `$` behavior is clarified:
- Cannot be combined with `$elemMatch` projection on the same field.
- `$elemMatch` in projection must not refer to a field already included.
- Ambiguous projection specifications now consistently error.

### 4.2 `$text` in Aggregation

The `$text` query operator is now supported in `$match` at non-first positions in the pipeline when used in combination with a text index, with some restrictions. (In 4.0 it could only be the first `$match`.)

## 5. Auth Changes in 4.4

### 5.1 Certificate Rotation Command

New command: `rotateCertificates`

```js
db.adminCommand({ rotateCertificates: 1 })
```

Triggers a live reload of TLS certificates without restarting the server. Requires the server to be started with `--tlsMode` settings.

**Source:** `src/mongo/db/commands/rotate_certificates_command.cpp`  
**IDL:** `src/mongo/db/commands/rotate_certificates.idl`

## 7. Commands Removed / Changed in 4.4

### 7.1 GeoHaystack Now Rejected on Creation

While haystack indexes are not formally removed until 5.0, in 4.4 the behavior when `createIndexes` is called with `"geoHaystack"` in the key is to return a deprecation warning and proceed. In 5.0, it returns an error.

## 8. Feature Compatibility Version in 4.4

```js
db.adminCommand({ setFeatureCompatibilityVersion: "4.4" | "4.2" | "4.0" })
```

Setting to "4.4" enables:
- `$unionWith` aggregation stage
- `$accumulator` custom accumulator
- `commitQuorum` on index builds

---

## 9. Breaking Changes from 4.2 → 4.4

1. **`background` option ignored:** The `background` field in `createIndexes` is silently ignored; all builds are background.
2. **`$` projection strictness:** Ambiguous projection specifications that were previously tolerated now consistently throw errors.
3. **GeoHaystack deprecation warning:** Creates a log warning when used.
4. **Index build behavior:** Index builds on replica sets now use two-phase protocol; in-progress builds can be monitored via `currentOp`.
