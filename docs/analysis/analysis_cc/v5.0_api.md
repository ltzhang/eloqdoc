## Summary of 5.0 Changes (Data Model Focus)

| Area | Change |
|---|---|
| **Collection types** | New: Time-series collections |
| **Aggregation** | New `$setWindowFields` stage with window functions |
| **Accumulators** | New window accumulators: covariance, exponential moving avg, integral, rank, dense_rank, documentNumber |
| **Pipeline internals** | New stages for time-series unpacking |
| **MapReduce** | Officially deprecated (use aggregation instead) |
| **Auth** | Certificate rotation improvements |
| **GeoHaystack** | Creation now rejected (index type removed) |
| **Versioned API** | New `apiVersion` / `apiStrict` / `apiDeprecationErrors` request parameters |
| **Commands** | `validate --repair` removed; `validateDBMetadata` added |

## 1. Index Types — Changes in 5.0

**No new index types added in 5.0.** Types remain: btree, 2d, 2dsphere, text, hashed, wildcard.

### 1.1 GeoHaystack Index Removed

The `geoHaystack` index type is **fully removed** in 5.0. Attempting to create a `geoHaystack` index returns an error:
```
"GeoHaystack indexes are no longer supported. Please drop any GeoHaystack indexes 
and use a different index type."
```

Existing `geoHaystack` indexes from prior versions are dropped automatically during the upgrade to 5.0.

## 2. Time-Series Collections (New in 5.0)

**Source directory:** `src/mongo/db/timeseries/`  
**IDL:** `src/mongo/db/timeseries/timeseries.idl`

Time-series collections are a new first-class collection type optimized for time-ordered data (IoT sensor readings, metrics, logs, financial ticks, etc.). They transparently bucket documents by time to improve storage density and query performance.

### 2.1 Creating a Time-Series Collection

```js
db.createCollection("<name>", {
  timeseries: {
    timeField: "<fieldName>",          // required: the timestamp field
    metaField: "<fieldName>",          // optional: grouping/metadata field
    granularity: "seconds" | "minutes" | "hours",  // default: "seconds"
    bucketMaxSpanSeconds: <int>,       // max time span per bucket (optional)
  },
  expireAfterSeconds: <int>            // optional: TTL for measurements
})
```

**`TimeseriesOptions` IDL fields:**

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `timeField` | string | yes | — | Must be a top-level field; stores Date values |
| `metaField` | string | no | — | Field used to group measurements into buckets |
| `granularity` | BucketGranularity enum | no | `"seconds"` | Controls bucket time span |
| `bucketMaxSpanSeconds` | int | no | — | Override for bucket time span; conflicts with granularity if both set |

**`BucketGranularity` enum values:**
| Value | Default bucket max span | Typical use |
|---|---|---|
| `"seconds"` | 3600 seconds (1 hour) | High-frequency sensor data |
| `"minutes"` | 86400 seconds (1 day) | Minute-resolution data |
| `"hours"` | 2592000 seconds (30 days) | Hourly or daily data |

**Server parameters from `timeseries.idl`:**

| Parameter | Default | Description |
|---|---|---|
| `timeseriesBucketMaxCount` | 1000 | Max measurements per bucket |
| `timeseriesBucketMaxSize` | 128000 bytes | Max bytes per bucket |
| `timeseriesBucketsCollectionClusterById` | true | Cluster the underlying `_id` |
| `timeseriesInsertMaxRetriesOnDuplicates` | 32 | Retries on duplicate bucket key |

### 2.2 How Time-Series Collections Work Internally

A time-series collection named `<name>` is stored as a view over a system buckets collection `system.buckets.<name>`. Users interact only with `<name>` via normal CRUD operations; the server transparently:
1. Routes inserts to the appropriate bucket (by `metaField` + time range).
2. Creates a new bucket document if no suitable one exists.
3. Unpacks bucket documents when returning results to the client.

**Bucket document format (internal, not user-visible):**
```
{
  _id: ObjectId,
  control: {
    version: 1,
    min: { time: Date, field1: value, ... },
    max: { time: Date, field1: value, ... }
  },
  meta: <metaField value>,
  data: {
    <timeField>: { "0": Date, "1": Date, ... },
    <field1>: { "0": val, "1": val, ... }
  }
}
```

### 2.3 Querying Time-Series Collections

Standard `find`, `aggregate`, and `count` work on time-series collections. The `$match` stage on `timeField` uses bucket-level min/max to skip entire buckets.

**Supported operations in 5.0:**
- `find` with filters on `timeField` and `metaField`
- `aggregate` with most stages
- Insert (single and bulk)
- No updates or deletes directly (added in later versions)

**Aggregation internal stage:** `$_internalUnpackBucket` — the query planner inserts this stage automatically to unpack the bucket format. Not user-accessible.

### 2.4 Time-Series Index Support in 5.0

Indexes on time-series collections in 5.0 are limited:
- An index on `metaField` is created automatically.
- Secondary indexes on other fields require a special conversion function.
- The underlying `system.buckets.*` collection uses clustered-by-`_id` storage.

Full secondary index support for time-series was expanded significantly in 6.0.

### 2.5 TTL on Time-Series Collections

`expireAfterSeconds` on a time-series collection sets a TTL based on the `timeField`:
```js
db.createCollection("temps", {
  timeseries: { timeField: "timestamp" },
  expireAfterSeconds: 86400    // keep data for 24 hours
})
```

## 3. Window Functions (`$setWindowFields`) — New in 5.0

**Source:** `src/mongo/db/pipeline/document_source_set_window_fields.cpp`  
**IDL:** `src/mongo/db/pipeline/document_source_set_window_fields.idl`

`$setWindowFields` enables running window functions over a sorted group of documents, similar to SQL window functions (`OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ...)`).

### 3.1 `$setWindowFields` Syntax

```js
{ $setWindowFields: {
    partitionBy: <expression>,           // optional; group documents
    sortBy: { field: 1 | -1 },          // optional; defines document order
    output: {
      <outputField>: {
        <windowOperator>: <expression>,
        window: {
          documents: [<lower>, <upper>],   // position-based: "current", "unbounded", or int
          range: [<lower>, <upper>],       // range-based (value or time offsets)
          unit: "millisecond" | "second" | "minute" | "hour" | "day" | "week" | "month" | "quarter" | "year"
        }
      }
    }
}}
```

**Window boundaries:**
- `"current"` — the current document
- `"unbounded"` — the start or end of the partition
- Integer N — N positions before (negative) or after (positive) current document
- Value offsets (for `range`) — numeric or date offsets from current value

### 3.2 Window Function Operators in 5.0

**Standard aggregation operators usable as window functions:**
`$sum`, `$avg`, `$min`, `$max`, `$count`, `$push`, `$addToSet`, `$first`, `$last`, `$stdDevSamp`, `$stdDevPop`

**New window-specific operators added in 5.0:**

| Operator | Description | Source file |
|---|---|---|
| `$covariancePop` | Population covariance of two values over the window | `accumulator_covariance.cpp` |
| `$covarianceSamp` | Sample covariance of two values over the window | `accumulator_covariance.cpp` |
| `$expMovingAvg` | Exponential moving average | `accumulator_exp_moving_avg.cpp` |
| `$integral` | Integral of a numeric expression over a time window | `accumulator_integral.cpp` |
| `$derivative` | Rate of change of a value over the window | (computed from integral) |
| `$rank` | Rank of the current document within partition (gaps on ties) | `accumulator_rank.cpp` |
| `$denseRank` | Dense rank (no gaps on ties) | `accumulator_rank.cpp` |
| `$documentNumber` | Sequential number within partition (1-based) | `accumulator_rank.cpp` |
| `$shift` | Value from another document at a specified offset | (window function) |
| `$linearFill` | Linear interpolation between known values | (added in 6.0 via `$fill` stage) |
| `$locf` | Last observation carried forward | (added in 6.0 via `$fill` stage) |

**`$expMovingAvg` specific options:**
```js
{ $expMovingAvg: {
    input: <expression>,
    N: <int>     // number of historical docs to use
    // OR
    alpha: <float>  // smoothing factor (0 < alpha <= 1)
}}
```

**`$integral` and `$derivative` options:**
```js
{ $integral: {
    input: <expression>,
    unit: "millisecond" | "second" | "minute" | "hour" | "day"
}}
```

## 4. New Aggregation Stages (Internal / Time-Series)

### 4.1 `$_internalUnpackBucket`

Internal stage injected by the planner for time-series collections. Not user-accessible.

Constants from `document_source_internal_unpack_bucket.h`:
- `kStageNameInternal = "$_internalUnpackBucket"`
- `kStageNameExternal = "$_unpackBucket"` (test only)
- `kInclude`, `kExclude` — projection mode
- `kUsesExtendedRange` — flag for pre-1970/post-2554 timestamps
- `kBucketMaxSpanSeconds`

### 4.2 `$_internalConvertBucketIndexStats`

Internal stage converting bucket-level index statistics to measurement-level statistics for the `$indexStats` stage on time-series collections.

### 4.3 `$_internalShredDocuments`

Internal stage for time-series bucket shredding during update/delete operations.

## 5. Versioned API (New in 5.0)

MongoDB 5.0 introduces a **Stable API** (also called Versioned API). Clients can declare which API version they require, and MongoDB will enforce compatibility guarantees.

### 5.1 Request-Level API Fields

These fields can be added to any command request:

| Field | Type | Default | Notes |
|---|---|---|---|
| `apiVersion` | string | — | Currently only `"1"` is supported |
| `apiStrict` | bool | false | If true, reject commands/options not in the declared API version |
| `apiDeprecationErrors` | bool | false | If true, error on use of deprecated features within the API version |

**Example:**
```js
db.runCommand({
  find: "orders",
  filter: { status: "pending" },
  apiVersion: "1",
  apiStrict: true
})
```

### 5.2 What Is in API Version 1

Commands with `api_version: "1"` in their IDL are guaranteed stable:
- `find`, `getMore`, `aggregate`
- `insert`, `update`, `delete`, `findAndModify`
- `createIndexes`, `dropIndexes`, `listIndexes`
- `create`, `drop`, `listCollections`
- `count` (deprecated in stable API), `distinct`
- `authenticate`, `logout`
- User and role management commands

**Not in API version 1 (subject to change):** Internal stages (`$_internal*`), some admin commands, experimental features.

## 7. CRUD Changes in 5.0

### 7.1 Insert into Time-Series Collections

Inserts into a time-series collection require the `timeField` to be present and a valid `Date`:
```js
db.temps.insertMany([
  { timestamp: new Date(), location: "NYC", temp: 72.5 },
  { timestamp: new Date(), location: "LA",  temp: 78.1 }
])
```

If `metaField` is configured, the `metaField` value is used to route documents to the same bucket.

### 7.2 No Atomic Updates/Deletes on Time-Series (5.0)

In 5.0, direct updates and deletes on time-series collections are **not supported**. Operations are rejected. To delete data, use the TTL mechanism. Updates/deletes were added in later versions.

## 8. MapReduce Deprecated

MapReduce is officially deprecated in 5.0. The command still works but emits a deprecation warning. The recommended migration path:

| MapReduce pattern | Aggregation equivalent |
|---|---|
| `map` + `reduce` over all docs | `$group` with accumulators |
| `map` + `reduce` with `query` | `$match` + `$group` |
| `finalize` step | `$addFields` or `$project` after `$group` |
| `out: "collection"` | `$out` or `$merge` |
| `out: { inline: 1 }` | Aggregation with no `$out` |

```js
db.adminCommand({

})
```

Checks that all indexes and collections in the specified database are compatible with the given API version.

## 11. Feature Compatibility Version in 5.0

```js
db.adminCommand({ setFeatureCompatibilityVersion: "5.0" | "4.4" })
```

Setting to "5.0" enables:
- Time-series collection creation
- `$setWindowFields` with all window functions
- Versioned API enforcement
- Removal of GeoHaystack index creation

**SetFCVPhase enum** (`src/mongo/db/commands/set_feature_compatibility_version.idl`):
- `kStart` — beginning of FCV change
- `kComplete` — FCV change committed

## 12. Breaking Changes from 4.4 → 5.0

1. **GeoHaystack creation rejected:** `createIndexes` with `"geoHaystack"` returns an error; existing indexes are dropped during upgrade.
2. **`background` option in `createIndexes` removed:** Silently ignored in 4.4, now produces a deprecation warning.
3. **MapReduce deprecation warnings:** All `mapReduce` invocations log a deprecation warning.
4. **FCV 4.4 required before upgrading to 5.0:** Cannot jump from FCV 4.2 directly to 5.0.
