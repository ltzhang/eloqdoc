# MongoDB 4.2 — API Delta from 4.0

**Source branch:** `origin/v4.2`  
**Baseline:** [v4.0_api.md](v4.0_api.md)  
**Format:** Explicit Added / Modified / Removed sections. Everything not mentioned here is unchanged from 4.0.

## Summary of 4.2 Changes (Data Model Focus)

| Area | Change |
|---|---|
| **Indexes** | New wildcard index type (`"wildcard"`) |
| **Aggregation** | New `$merge` output stage; new `$planCacheStats` stage |
| **Pipeline internals** | `$exchange` (internal), trigonometric expression functions |

## 1. Index Types — Changes

### 1.1 New: Wildcard Index (`"wildcard"`)

**Added in 4.2.** Defined in `src/mongo/db/index_names.h` as `INDEX_WILDCARD` with string `"wildcard"`.

**Access method source:** `src/mongo/db/index/wildcard_access_method.cpp`  
**Key generator source:** `src/mongo/db/index/wildcard_key_generator.cpp`

**Purpose:** Index all fields (or all sub-fields within a path) automatically, without specifying individual field names. Useful when documents have varying or unknown field names.

**Key pattern formats:**
```js
{ "$**": 1 }                    // index all fields in every document
{ "a.$**": 1 }                  // index all sub-fields under "a"
{ "$**": 1, wildcardProjection: { "b": 0 } }  // exclude field "b"
{ "$**": 1, wildcardProjection: { "c": 1 } }  // include only field "c"
```

**Extra `createIndexes` fields for wildcard:**

| Field | Type | Default | Notes |
|---|---|---|---|
| `wildcardProjection` | object | — | Inclusion or exclusion projection applied to the wildcard; cannot mix include and exclude except `_id` |

**Restrictions in 4.2:**
- Cannot be a unique index.
- Cannot be a hashed, TTL, or 2d/2dsphere index simultaneously.
- Cannot be used as the shard key.
- Cannot be a compound index (only one field, which must be `$**` or `path.$**`). Compound wildcard indexes were added in **6.0**.
- `wildcardProjection` must use pure inclusion or pure exclusion.

**Query planning:** Wildcard index can satisfy equality, range, prefix, and existence queries for any indexed field. For a query on a specific field, the planner extracts the portion of the wildcard index that covers that field.

### 1.2 `existedBefore24()` Removed

The `existedBefore24()` method on `IndexNames` is removed in 4.2. It was a historical artifact.

### 1.3 `nameToType()` Signature Change

Changed from `const std::string&` parameter to `StringData` parameter — internal API change affecting C++ plugins.

## 2. Aggregation Pipeline — Changes

### 2.1 New Stage: `$merge`

**Source:** `src/mongo/db/pipeline/document_source_merge.cpp`  
**IDL:** `src/mongo/db/pipeline/document_source_merge.idl`  
**Mode enum IDL:** `src/mongo/db/pipeline/document_source_merge_modes.idl`

`$merge` is a more powerful replacement for `$out`. It can write pipeline results to an existing collection, merging with existing documents rather than always replacing the entire collection.

```js
{ $merge: {
    into: "<collection>" | { db: "<db>", coll: "<collection>" },
    on: "<field>" | [ "<field>", ... ],  // default: "_id"
    let: { var: "$$<var>" },
    whenMatched: "replace" | "keepExisting" | "merge" | "fail" | [ <pipeline> ],
    whenNotMatched: "insert" | "discard" | "fail"
}}
```

**`on` field:** The identity field(s) for matching documents. There must be a unique index on these fields in the target collection.

**`whenMatched` options:**
| Value | Behavior |
|---|---|
| `"replace"` | Replace the matched document entirely |
| `"keepExisting"` | Keep the existing document, discard the new one |
| `"merge"` | Merge new document fields into existing document |
| `"fail"` | Throw error if match found |
| `[<pipeline>]` | Run a custom pipeline; can use `$$new` and `$$ROOT` |

**`whenNotMatched` options:**
| Value | Behavior |
|---|---|
| `"insert"` | Insert new document |
| `"discard"` | Discard new document |
| `"fail"` | Throw error |

**Key differences from `$out`:**
- `$out` always replaces the target collection atomically.
- `$merge` can update individual documents in an existing collection.
- `$merge` supports cross-database writes (different `db` in `into`).
- `$merge` requires a unique index on the `on` field(s).

### 2.2 New Stage: `$planCacheStats`

**Source:** `src/mongo/db/pipeline/document_source_plan_cache_stats.cpp`

Returns plan cache entries for the collection.

```js
db.collection.aggregate([{ $planCacheStats: {} }])
```

Each output document represents one plan cache entry with fields: `createdFromQuery`, `isActive`, `works`, `queryHash`, `planCacheKey`, `cachedPlan`, `creationExecStats`, `candidatePlanScores`.

### 2.3 New Stage: `$exchange` (internal)

**Source:** `src/mongo/db/pipeline/document_source_exchange.cpp`

Internal stage used by the query planner for parallel aggregation execution. Not user-visible in query results. Used with `ExchangeSpec` IDL.

### 2.4 New Expression Functions (Trigonometric)

**Source:** `src/mongo/db/pipeline/expression_trigonometric.cpp`

New mathematical expressions added:
| Expression | Description |
|---|---|
| `$sin` | Sine of angle in radians |
| `$cos` | Cosine of angle in radians |
| `$tan` | Tangent of angle in radians |
| `$asin` | Arcsine; result in radians |
| `$acos` | Arccosine; result in radians |
| `$atan` | Arctangent; result in radians |
| `$atan2` | Arctangent of y/x; `{ $atan2: [y, x] }` |
| `$asinh` | Hyperbolic arcsine |
| `$acosh` | Hyperbolic arccosine |
| `$atanh` | Hyperbolic arctangent |
| `$sinh` | Hyperbolic sine |
| `$cosh` | Hyperbolic cosine |
| `$tanh` | Hyperbolic tangent |
| `$degreesToRadians` | Convert degrees to radians |
| `$radiansToDegrees` | Convert radians to degrees |

Also added: `$round` (round to N decimal places), `$trunc` (truncate to N decimal places).

## 3. Update Command — Aggregation Pipeline Form

**Added in 4.2.** The `u` field in an `updates` element can now be an aggregation pipeline (array of stages), not just an update document.

```js
db.runCommand({
  update: "<collection>",
  updates: [{
    q: <filter>,
    u: [   // ← ARRAY = aggregation pipeline form (NEW in 4.2)
      { $set: { total: { $add: ["$price", "$tax"] } } },
      { $unset: ["temp_field"] }
    ],
    upsert: false,
    multi: false
  }]
})
```

**Stages allowed in update pipeline:**
- `$addFields` / `$set` — add or update fields using expressions
- `$project` / `$unset` — remove fields
- `$replaceRoot` / `$replaceWith` — replace root document

This enables referencing existing field values in updates (e.g., incrementing a field based on another field's value), which was previously impossible with standard update operators alone.

**`findAndModify` also supports pipeline form for `update` field in 4.2.**

## 4. Client-Side Field Level Encryption (CSFLE)

**Added in 4.2.** Source: `src/mongo/db/matcher/schema/encrypt_schema.idl`

CSFLE is a client-side feature — the MongoDB server itself receives pre-encrypted BSON binary values (subtype 6). The server stores and returns encrypted blobs without being able to decrypt them.

### 4.1 Schema-Level Encryption Specification

The `encryptMetadata` and `encrypt` keywords are added to JSON Schema validation:

```js
{
  $jsonSchema: {
    properties: {
      ssn: {
        encrypt: {
          keyId: [UUID("...")],         // or "/path" for per-document key
          bsonType: "string",
          algorithm: "AEAD_AES_256_CBC_HMAC_SHA_512-Deterministic"
                   | "AEAD_AES_256_CBC_HMAC_SHA_512-Random"
        }
      }
    },
    encryptMetadata: {
      keyId: [UUID("...")],             // default key for all encrypted fields
      algorithm: "..."
    }
  }
}
```

**Algorithms:**
- `AEAD_AES_256_CBC_HMAC_SHA_512-Deterministic` — same plaintext always produces same ciphertext; supports equality queries.
- `AEAD_AES_256_CBC_HMAC_SHA_512-Random` — non-deterministic; cannot be queried directly; better security.

### 4.2 Encrypted BSON Binary Subtype

Encrypted fields are stored as BSON Binary with subtype `6` (BinData 6). The client driver handles encryption/decryption transparently when a mongocryptd or libmongocrypt is configured.

### 4.3 Server-Side Behavior

The server in 4.2 validates the JSON Schema to ensure `encrypt` specifications are syntactically correct. It does **not** decrypt values — it only:
- Rejects plaintext writes to fields marked as `encrypt` when `bypassDocumentValidation: false`
- Stores and retrieves the encrypted binary blobs

### 4.4 Key Management

Encryption keys are stored in a separate key vault collection (typically `__keyVault.datakeys`). Keys can be stored in:
- Local key file (for testing)
- AWS KMS
- Azure Key Vault
- GCP KMS

This is managed entirely by the client driver and mongocryptd — no server-side key management in 4.2.

## 5. Commands Removed in 4.2

The following commands were **removed** in 4.2 (deprecated in 4.0):

| Command | Reason / Replacement |
|---|---|
| `clone` | Use `mongodump` + `mongorestore`, or Atlas Live Import |
| `copydb` | Same as above |
| `copydbsaslstart` | SASL auth helper for copydb; also removed |
| `eval` | Server-side JavaScript execution; removed for security; no direct replacement |
| `geoNear` (command) | Use `$geoNear` aggregation stage instead |
| `group` | Use `$group` in aggregation pipeline instead |
| `parallelCollectionScan` | No direct replacement; use normal find/aggregation |
| `do_txn` (internal) | Replaced by internal transaction machinery |
| `invalidateViewCatalog` (internal) | Removed internal cache invalidation command |

**Implementation note for backport:** If implementing 4.2 forward compat on 4.0 codebase, these commands should return `CommandNotFound` error (code 59) when called by clients expecting 4.2 behavior. The commands exist in 4.0 codebase — you either leave them or disable them based on FCV.

## 6. Commands Added in 4.2

### 6.1 `dropConnections`

```js
db.adminCommand({
  dropConnections: 1,
  hostAndPort: ["host:port", ...]
})
```

Drops connections to specified hosts. Useful for testing connection failures.

### 6.2 HTTP Client Commands

`httpClientRequest` — internal command for making HTTP requests from the server. Used primarily for Cloud automation and KMS key fetching. Not a user-facing data API.

### 6.3 Traffic Recording Commands

`startRecordingTraffic` / `stopRecordingTraffic` — records network traffic to a file for replay testing.

### 6.4 Index Build Coordination

`voteCommitIndexBuild` — internal command for replica set index build voting coordination (part of the two-phase index build protocol introduced in 4.4, backported to 4.2).

## 7. IDL-Based Command Definitions

4.2 begins a systematic shift to IDL (Interface Definition Language) for command schema definitions. This is an internal tooling change but has API implications:
- Commands now have formal schemas in `.idl` files
- Unknown fields are more strictly rejected at the parser level
- Command `apiVersions()` method begins to appear in the codebase

**Files added in 4.2 (IDL):**
- `src/mongo/db/commands/create.idl` — collection creation schema
- `src/mongo/db/commands/feature_compatibility_version.idl` — FCV command
- `src/mongo/db/commands/parameters.idl` — server parameter setters
- `src/mongo/db/commands/sessions_commands.idl` — session management
- `src/mongo/db/commands/txn_cmds.idl` — transaction commands
- `src/mongo/db/commands/txn_two_phase_commit_cmds.idl` — 2PC
- `src/mongo/db/commands/user_management_commands.idl` — user/role management

## 8. Pipeline Architecture Changes (Internal)

### 8.1 New Process Interface Abstraction

`src/mongo/db/pipeline/mongo_process_interface.cpp` — abstraction layer separating pipeline execution from the underlying MongoDB service context. Enables cleaner testability and sharded aggregation.

Key variants:
- `MongoProcessInterface` — abstract base
- `MongoDProcessInterface` — standalone mongod implementation
- `MongosProcessInterface` — mongos (router) implementation

### 8.2 Stage Constraints System

`src/mongo/db/pipeline/stage_constraints.cpp/h` — formal model for pipeline stage constraints:
- `PositionRequirement` — must be first stage, etc.
- `HostTypeRequirement` — must run on primary/any
- `DiskUseRequirement` — whether the stage can spill to disk
- `FacetRequirement` — whether stage is allowed inside `$facet`
- `StreamType` — streaming vs. blocking

### 8.3 Pipeline Metadata Tree

`src/mongo/db/pipeline/pipeline_metadata_tree.h` — tree structure tracking metadata (field availability, sort order) through pipeline transformations.

## 10. Feature Compatibility Version in 4.2

```js
db.adminCommand({ setFeatureCompatibilityVersion: "4.2" | "4.0" })
```

Setting FCV to "4.2" enables:
- Wildcard index creation
- `$merge` aggregation stage
- Aggregation pipeline updates
- CSFLE schema enforcement

Setting FCV to "4.0" prevents creation of wildcard indexes but does not remove existing ones.

## 11. Breaking Changes from 4.0 → 4.2

1. **Commands removed:** `eval`, `clone`, `copydb`, `group`, `geoNear` (cmd), `parallelCollectionScan` — any code calling these will receive `CommandNotFound`.
2. **`$out` behavior:** `$out` in 4.2 no longer creates a temp collection and atomically renames; it locks the target collection. (The atomic rename behavior moved to `$merge`.)
3. **Distributed transactions:** Now supported across shards — significant internal change but the API (`startTransaction`, `commitTransaction`, `abortTransaction` in session context) remains the same as 4.0.
4. **Index names:** `nameToType()` now takes `StringData` instead of `std::string` — affects any C++ plugin code.
